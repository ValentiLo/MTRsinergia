## Кейс № 1. «Стартап на 5 человек: где собирать билды?»

### Анализ ситуации
- Команда: 5 человек, мобильная игра на Unity.
- Оборудование: 3 Mac mini (2018), 2 Windows-ноутбука.
- Проблема: сборка iOS занимает **45 минут** на одном Mac mini.

### Варианты решения

| Вариант | Плюсы | Минусы |
|---|---|---|
| **Оставить локально** | Бесплатно | Медленно, Mac mini занят, нельзя работать параллельно |
| **Dockerized Unity Accelerator** | Ускорение сборки на 30–40%, кэширование | Требует настройки, нужен сервер |
| **Amazon EC2 Mac Instances** | Мощные машины, оплата по факту, масштабируемость | Дорого, зависимость от интернета |
| **Гибрид: локально + облако для пиков** | Баланс цены и скорости | Сложнее в настройке |

### Рекомендация
**Гибридный подход:**
1. Настроить **Dockerized Unity Accelerator** на локальном сервере — это ускорит сборку на 30–40% .
2. Использовать **кастомные AMI с кэшированными репозиториями** — сократит время на скачивание зависимостей.
3. Для пиковых нагрузок — арендовать **Amazon EC2 Mac Instances** (например, на ночь или на время спринта).
4. Настроить **CI/CD** (GitHub Actions или Jenkins) для автоматизации сборок.

**Обоснование:** Реальный опыт **Good Job Games** показал, что такая схема ускорила сборку iOS на **43%** .

## Кейс № 2. «Распределённая команда: как синхронизировать ресурсы?»

### Анализ ситуации
- 40 человек в 3 городах.
- Проект на Unreal Engine 5, терабайты ассетов.
- Проблема: Git не справляется, синхронизация занимает часы.

### Варианты решения

| Вариант | Плюсы | Минусы |
|---|---|---|
| **Git + Git LFS** | Привычно, бесплатно | LFS ограничен по объёму, медленно для больших файлов |
| **Perforce (Helix Core)** | Стандарт игровой индустрии, быстрый для бинарных файлов | Дорого, требует сервера |
| **SVN** | Проще, чем Git | Устарел, медленный |
| **Облачное хранилище (S3) + Git для кода** | Гибко | Сложно синхронизировать |

### Рекомендация
1. **Перейти на Perforce (Helix Core)** — это стандарт для AAA-проектов с большими бинарными файлами.
2. **Организовать сеть:**
   - Выделенные каналы между городами (VPN или MPLS).
   - Пропускная способность: **не менее 100 Мбит/с** на город.
   - Локальные кэширующие серверы (Perforce Proxy) в каждом городе.
3. **Репликация:** настроить **Perforce Replica** для чтения — художники работают с локальной копией, не нагружая основной сервер.
4. **Резервное копирование:** ежедневный бэкап депо на отдельный сервер.

**Обоснование:** Perforce специально оптимизирован для больших бинарных файлов и используется в **Ubisoft, EA, Rockstar** .

## Кейс № 3. «Художник против программиста: одно железо — разные требования»

### Анализ ситуации
- Бюджет ограничен, нужно 10 станций.
- Технический директор предлагает одинаковые машины для всех.
- Художник хочет больше видеопамяти, программист — больше ядер.

### Варианты решения

| Роль | Что важно | Рекомендуемая конфигурация |
|---|---|---|
| **Программист** | Много ядер (компиляция) | AMD Threadripper / Ryzen 9, 128 ГБ RAM, RTX 5070 Ti |
| **Художник** | Видеопамять + одноядерная | Intel Core Ultra 9, 96 ГБ RAM, RTX 5080 |
| **Универсальная** | Баланс | Intel Core i9, 64 ГБ RAM, RTX 4080 |

### Рекомендация
**Разделить закупку:**
- **4 станции для программистов:** акцент на CPU (12+ ядер), 128 ГБ RAM, средняя видеокарта.
- **4 станции для художников:** акцент на GPU (16+ ГБ видеопамяти), 96 ГБ RAM, топовый CPU.
- **2 универсальные станции** для тестировщиков и менеджеров.

**Обоснование:**
- Программисты компилируют код **десятки раз в день** — им нужны ядра.
- Художники работают с текстурами 4K/8K и рендерингом — им нужна видеопамять.
- Одинаковые машины для всех — **переплата** за ненужные функции .

## Кейс № 4. «Облако или локальный сервер?»

### Анализ ситуации
- 120 разработчиков.
- CAPEX (локально): ~$800,000.
- OPEX (облако): ~$280,000/год.

### Сравнение

| Критерий | Локально | Облако |
|---|---|---|
| **Начальные затраты** | Высокие ($800K) | Низкие |
| **Ежегодные затраты** | ~$100K (обслуживание) | $280K |
| **Масштабируемость** | Ограничена | Высокая |
| **Контроль** | Полный | Ограничен |
| **Безопасность** | Полный контроль | Зависит от провайдера |
| **Окупаемость** | 3–4 года | Бессрочно |

### Рекомендация
**Гибридная модель:**
1. **Критичные данные** (исходники, билды, аналитика) — **локально**.
2. **Пиковые нагрузки** (сборки, тесты, рендеринг) — **в облаке** (AWS, Azure, GCP).
3. **Резервное копирование** — в облако (S3, Glacier).

**Обоснование:** Гибридная модель даёт **экономию 30–40%** по сравнению с чистым облаком и **гибкость** по сравнению с чистым локальным решением .

## Кейс № 5. «DDoS-атака на этапе плейтестов»

### Анализ ситуации
- Плейтест многопользовательской игры.
- Внезапно — тысячи запросов в секунду.
- Плейтестеры не могут подключиться.

### Рекомендации

**1. Защита на уровне сети:**
- **DDoS-защита** от провайдера (AWS Shield, Cloudflare).
- **Веб-application firewall (WAF)** для фильтрации трафика.
- **Rate limiting** — ограничение числа запросов с одного IP.

**2. Сегментация сети:**
- **DMZ** для публичных серверов.
- **Внутренняя сеть** для БД и админ-панелей.
- **VLAN** для разделения трафика.

**3. Мониторинг и реагирование:**
- **IDS/IPS** (Snort, Suricata) — обнаружение вторжений.
- **SIEM** (Splunk, ELK) — анализ логов.
- **Автоматическое масштабирование** — добавление серверов при атаке.

**4. Аутентификация:**
- **Многофакторная аутентификация** для админов.
- **Токены** для API.

**Обоснование:** Такие меры описаны в исследованиях по **кибербезопасности игровых проектов** .

## Кейс № 6. «Глобальный плейтест: как учесть региональные задержки?»

### Анализ ситуации
- Игроки в Северной Америке, Европе, Азии.
- Пинг у азиатских игроков — **250 мс**.

### Рекомендации

**1. Региональные серверы:**
- Развернуть серверы в **3 регионах**: US-East, EU-West, Asia-Southeast.
- Использовать **AWS GameLift** или **Azure PlayFab** для управления.

**2. CDN для контента:**
- **CloudFront, Cloudflare, Akamai** — кэширование ассетов ближе к игрокам.

**3. Оптимизация протоколов:**
- **UDP** вместо TCP для игрового трафика.
- **Клиентская предсказание** (client-side prediction).
- **Интерполяция** и **экстраполяция** позиций.

**4. Метрики:**
- **RTT (round-trip time)** — задержка.
- **Jitter** — вариация задержки.
- **Packet loss** — потери пакетов.

**Обоснование:** Географически распределённые плейтест-среды — стандарт для глобальных игр .

## Кейс № 7. «Сборка на Mac: почему так долго?»

### Анализ ситуации
- Unity, iOS-сборка — 1 час на Mac mini.
- Нужно ускорить без покупки нового железа.

### Рекомендации

**1. Dockerized Unity Accelerator:**
- Кэширует импортированные ассеты.
- Ускоряет повторные сборки на **30–40%**.

**2. Кастомные AMI с кэшированными репозиториями:**
- Предустановленные зависимости.
- Быстрый старт сборки.

**3. Amazon EC2 Mac Instances:**
- Аренда на время сборки.
- Оплата по факту.

**4. Параллельные сборки:**
- Разделить сборку на этапы (компиляция, линковка, упаковка).
- Запускать на разных машинах.

**Обоснование:** **Good Job Games** использовала именно такую схему, ускорив сборку на **43%** .

## Кейс № 8. «Удалённая работа: как дать доступ к мощным станциям?»

### Анализ ситуации
- Сотрудники работают из дома.
- Личные ноутбуки не тянут Unreal Engine 5.

### Рекомендации

**1. Решения для удалённого доступа:**
- **Amazon DCV** — потоковая передача рабочих станций с GPU.
- **Parsec, Moonlight** — для художников.
- **RDP + GPU** — для программистов.

**2. Безопасность:**
- **VPN** (OpenVPN, WireGuard) — шифрованный канал.
- **MFA** — многофакторная аутентификация.
- **Active Directory** — централизованное управление доступом.

**3. Требования к каналу:**
- Скачивание: **не менее 25 Мбит/с**.
- Отдача: **не менее 10 Мбит/с**.
- Задержка: **не более 30 мс**.

**Обоснование:** Amazon DCV интегрируется с VPN и Active Directory, обеспечивая безопасный доступ .

## Кейс № 9. «Аналитика после релиза: что делать с данными?»

### Анализ ситуации
- Игра вышла, нужно понимать поведение игроков.
- Данные с клиентов, серверов, бэкенда.

### Рекомендации

**1. Пайплайн аналитики:**
- **Сбор:** SDK на клиенте + серверные логи.
- **Транспорт:** AWS Kinesis, Kafka.
- **Хранение:** S3, Redshift, ClickHouse.
- **Обработка:** Spark, Flink.
- **Визуализация:** Grafana, Tableau, Power BI.

**2. Метрики:**
- **DAU/MAU** — активные пользователи.
- **Retention** — удержание.
- **LTV** — пожизненная ценность.
- **ARPU** — средний доход на пользователя.
- **CCU** — одновременные игроки.

**3. Реальное время:**
- **CloudWatch, Prometheus** — мониторинг.
- **Alerting** — оповещения при аномалиях.

**Обоснование:** Такие пайплайны описаны в практике **игровой аналитики** .

## Кейс № 10. «Своя инфраструктура или готовые облачные сервисы?»

### Сравнение

| Критерий | Локально | Облако (GameLift, PlayFab) |
|---|---|---|
| **Начальные затраты** | Высокие | Низкие |
| **Гибкость** | Полная | Ограничена провайдером |
| **Масштабируемость** | Ограничена | Автоматическая |
| **Обслуживание** | Своими силами | Провайдер |
| **Безопасность** | Полный контроль | Зависит от провайдера |
| **Стоимость** | CAPEX + OPEX | OPEX |

### Рекомендация

**Для мультиплеерной игры:**
- **Стартап / инди:** облачные сервисы (AWS GameLift, Azure PlayFab) — быстрый старт, низкие затраты.
- **Средняя студия:** гибрид — критичное локально, пиковое в облаке.
- **AAA-студия:** собственная инфраструктура + облако для пиков.

**Обоснование:** Выбор зависит от **бюджета, масштаба и требований к контролю** .
